# 项目面试：20 个高概率追问与口述答案

每个答案按正常语速约 30–60 秒。先理解再用自己的话说，不背“技术名词串”。以下只讲已实现功能，不宣称线上大规模运行或绝对消除幻觉。

## 1. 你这个项目解决了什么问题？

我做的是工作复盘平台，解决两个问题：输入很模糊时，大模型容易写成空话；积累很多周报后，用户又很难知道计划是否真正推进。我的流程是先判断信息是否充分，必要时追问最多三个问题，允许跳过并保留不确定性。生成后用户确认保存。历史复盘和计划分析会检索原文，并给结论附依据。重点不是换个聊天界面，而是把事实输入、模型决策、证据核对和确认保存做成可用闭环。

## 2. 它为什么能叫 Agent，不是普通 API 调用？

普通生成和重写确实主要是单次模型润色，我不会把它们都说成 Agent。复盘和计划分析不同：模型可以根据当前信息选择搜索、读取哪些记录，拿到工具结果后继续决定下一步，直到输出结果或预算终止。服务端没有预先固定所有查询顺序，而是提供白名单工具和可控循环。模型决定路径，服务端决定权限、预算和最终结果能否通过校验，这就是项目中明确的 Agent 特征。

## 3. Tool Calling 实际上是谁执行工具？

模型并没有执行数据库函数。它返回 assistant.tool_calls，包含名称、JSON 参数和调用 ID。我在服务端解析参数，检查工具是否在白名单，按 Schema 做第二次校验，然后执行对应函数。工具拿到的 userId 来自服务端 JWT 上下文。执行结果作为 role:tool 消息，带相同 tool_call_id 回传，模型再继续推理。这样模型请求能力与应用执行权限是分开的，也不会直接接触数据库连接或模型密钥。

## 4. 为什么不用 LangChain 或 LangGraph？

这个项目的任务数量有限，工具只有少量明确的数据库操作。直接使用 DeepSeek 协议和一个通用 runAgent，已经可以实现循环、错误回传、预算、取消与校验。引入更大的框架不一定能解决当前业务问题，反而增加我需要解释的抽象。我的取舍是把协议和业务边界做清楚，任务规则通过配置复用同一个 Runtime；没有因为工具数量增加就复制一套执行器，也没有做多个 Agent 的自治协作。

## 5. 你的 Agent Loop 如何结束？

每轮先检查取消、上下文和 Token 预算，然后请求模型。有工具请求就验证并执行，把结果加入历史，继续下一轮。没有工具请求时才校验最终 JSON。通过就返回，失败会告诉模型具体问题，最多修订两次。与此同时还有八轮响应、十二次工具、总时间和输出限制。所以结束既可能是可靠结果，也可能是明确错误，不会为了看起来成功而无限循环，或者接受 finish_reason 为 length 的截断结果。

## 6. 怎么防止跨用户读取？

用户身份只从验证后的 JWT 获得，前端和模型参数都不能指定可信 userId。所有历史查询和详情读写都带 user_id，详情同时带 id。Tool Schema 也不包含 userId，多传这个字段会在 SQL 前被拒绝。草稿会话同样检查所属用户。我分别测试了用户查询其他人的计划、读取其他人的周报以及确认其他人的草稿，这些都不会返回内容或产生写入。按钮隐藏只是交互，真正权限在服务端。

## 7. 为什么需要服务端二次参数校验？

Schema 提供给模型只是告诉它怎样调用，不代表返回值一定正确。模型可能给字符串 ID、越界数量、多余字段，数据里也可能有诱导指令。所以服务端仍检查对象结构、必填字段、类型、长度和范围，未知工具也直接拒绝。只有验证通过才调用函数。可修正的输入错误可以回传给模型调整，但数据库故障不能包装成空查询结果，否则模型会把服务不可用误认为没有证据。

## 8. 智能追问和固定问卷有何区别？

我没有在前端固定几个问题。模型根据本次输入判断是否存在影响事实准确性的缺口，充分时返回空数组，不足时最多三个问题。每个问题都必须关联用户本次输入中的真实 anchor，不能生成答案或 HTML。前端只是按结构化 JSON 渲染表单。历史可以辅助理解已经发生的工作，但不能把上周状态直接当本周状态。用户可以跳过，系统保留待确认信息，不把跳过理解成允许模型猜测。

## 9. 补充以后如何保持同一会话？

准备阶段在服务端创建草稿，保存原输入、问题和历史快照，返回 sessionId。用户回答时按 questionId 提交，服务端校验每个答案属于这份草稿，再将真实补充合并回原字段。原输入不会被前端随意替换，历史也有本次快照。因此后续生成是在继续同一份材料。会话有用户所有权和有效期，不在等待回答时维持长连接。重启会丢失未保存会话，这个限制会明确显示，不会写成已经保存成功。

## 10. 如何避免模型虚构事实？

我分层降低风险：提示词禁止新增成果、数字和状态；追问让缺口显式化；生成后检查输入未提供的数字和部分未经确认的完成表述。如果发现这类问题，不追加无限重试，而是直接保留原输入做保守整理，并显示回退提示。最终仍需用户确认。复盘和计划另外做原文引用校验。我不会说这些规则能消除全部幻觉，尤其文本润色的语义正确性仍需人审阅，这是项目明确的工程边界。

## 11. Evidence 校验具体校验了什么？

它先检查引用格式，再检查 reportId 是否属于本次实际读取的快照，field 是否允许，quote 是否是该字段中的连续片段，只允许规范化空白。这样能拦截没读的 ID、改写的引用和超出截断范围的内容。复盘的连续性与反复问题还需要多个来源，计划再检查顺序和明确状态。但“引用真实存在”不等于“引用充分支持推论”，所以结果仍可展开原文让用户核对，不把出处验证包装成完整的事实证明。

## 12. 没有提到计划时，为什么不是未完成？

周报不是完整事件日志，遗漏可能只是用户没写，也可能是事项已完成但没描述。没有出现不能证明未完成。因此我的状态只有已完成、进行中、阻塞和无法确认，没有自动判定未完成。每项计划先查后续记录，没有明确相关证据就 unconfirmed。此时 Evidence 包含原计划，只证明计划存在，原因明确说当前记录不足。不会拿“没有命中关键词”作为负面绩效判断，也不会自行补根因。

## 13. 如何确定完成证据对应同一个计划？

先由 get_recent_plans 读取原计划，服务端生成 planId；检索限定在该记录之后。引用必须来自实际检索并读取的后续记录，不能引用旧成果或 next_plan 本身。除了 quote 检查，我还用保守的事项名称匹配和明确状态词检查，拒绝未来计划、否定完成和其他模块的成果。代价是别名或复杂表述可能无法匹配而返回无法确认。我接受这种偏保守结果，避免误把无关成果认成已完成。

## 14. 为什么生成后不自动入库？

模型完成响应不等于用户认可它。我的生成结果先存为临时草稿，浏览器显示预览，完整流和校验通过后才开放确认保存。确认接口检查会话所有权、草稿状态、正文一致以及 confirm=true。模型可用工具里没有写工具，因此不能自主修改正式周报。原有 AI 重写也是预览后手动保存。这样把模型建议和真实记录分开，用户可以检查、放弃，而不是把一次失败或不合意的输出变成历史事实。

## 15. 重复保存怎么保证幂等？

前端禁用按钮只能减少重复点击，不能防网络重试或并发请求。我给每份草稿使用同一个 UUID，并在 reports 加 UNIQUE(user_id, request_key)。确认 INSERT 碰到同一键不会创建新记录，然后核对已有正文并返回同一 reportId。内存的 saved 状态只是快速路径，数据库索引才是最终保证。测试覆盖并发确认和模拟响应丢失后的重试，还在真实 MySQL 临时表验证最终只有一条记录，不写真实用户数据。

## 16. SSE 为什么要缓冲，怎么处理中文？

网络块不保证恰好是一条事件，一个块可能包含多条，也可能只有半条 JSON，中文字符也可能跨字节块。前端用 TextDecoder 流模式解码，积累 buffer 后按空行取完整事件。后端用 StringDecoder 处理上游 UTF-8，再转成自己的 content 事件。最终结果还要求 DONE，异常断流不能算成功。这个设计保留实时输出体验，同时把“看到了部分文本”和“得到完整可确认草稿”明确区分。

## 17. 停止和超时如何影响数据库？

客户端 AbortController 中断 fetch，服务端监听响应关闭并取消上游模型；Runtime 每个边界还检查信号，因此迟到结果不会触发下一轮。已发出的 MySQL SELECT 可能仍在服务器执行，但结果会被丢弃。生成本身不写库，所以中止不会创建正式周报。用户已经明确确认的写入不能因为浏览器断开就假装取消，如果响应丢失可以用原请求键重试。任务还设总超时，不能只依赖模型单次 HTTP 超时。

## 18. 你做了哪些真实测试，哪些不是？

单元测试覆盖工具非法参数、跨用户、引用、循环预算、取消超时、追问、跳过和确认幂等；前端测试覆盖分块流、断流与续接协议。真实模型验收用合成周报跑追问、跳过、四种计划状态、Phase 1 和重写。MySQL 验收检查真实查询与临时表写入幂等。界面也用合成输入验证追问和草稿。它们能证明这些链路可运行，但不是长期线上准确率或负载测试，我不会虚构评测规模。

## 19. 当前最大工程限制是什么？

当前仍是作品集应用。草稿和Run已经存MySQL，可以恢复结果或安全重跑，同requestKey有数据库租约；用户并发锁和限流仍是进程内。历史没有所属周期和版本字段，创建时间不能等同工作发生时间。Hybrid RAG有候选上限，缺Embedding配置会明确降级；状态词检查会有保守误拒绝。新增RAG、Trace与持久化的15个面试问题见AGENT_PROJECT_LEARNING.md第17节。

## 20. 如果让你演示核心亮点，你会演示什么？

我先用充分输入证明它不强制追问，再用模糊权限模块输入展示结构化问题和跳过后的待确认信息。然后生成草稿，确认前历史不变，确认后只增加一条，重复提交仍是同一记录。最后选择历史计划，展示完成、进行中、阻塞和无法确认，并打开原文证据。面试讲解围绕模型如何选工具、权限由谁限制、引用如何校验以及谁有权写入，这些都能在代码和测试中核对，不靠口头包装。
